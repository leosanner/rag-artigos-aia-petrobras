# F-11 Block 02 — Persistence: Tool-Call Audit and Run Mode

## Goal

Extend the governance schema to record agentic-turn evidence without
breaking F-05 / F-06 / F-08 contracts. The result is a child table for
per-step tool calls and three new columns on `rag_query_runs` describing
how the turn ran.

## Scope

**In scope:**

- New table `rag_query_run_tool_calls` with FK to `rag_query_runs(id)`,
  `ON DELETE CASCADE`, and a unique constraint on
  `(query_run_id, step_index)`.
- New columns on `rag_query_runs`:
  - `execution_mode text not null default 'single_shot'`
    (CHECK constraint: `'single_shot' | 'agentic'`).
  - `agent_steps int null` (CHECK: `agent_steps >= 0` when not null).
  - `agent_stopped_reason text null` (CHECK:
    `'finished' | 'max_steps' | 'error'` when not null).
- A backfill that sets `execution_mode = 'single_shot'` for all existing
  rows. (Default already does this; explicit step exists only if the
  default is added in a separate statement.)
- Drizzle schema definitions in `src/db/schema.ts` mirroring the SQL.
- A migration generated by `pnpm db:generate` and committed under
  `drizzle/`.
- Repository functions:
  - `ragQueryRunToolCallsRepository.insertMany(rows)` — bulk insert in
    `step_index` order inside the same transaction as the parent run.
  - `ragQueryRunsRepository.persistAgenticRun(...)` (or extension of the
    existing persist function) — accepts the new columns.
- Repository tests against a real Postgres (per project convention).

**Out of scope:**

- Surfacing tool calls in any API response body. The audit endpoints
  may eventually expose them, but that is not part of F-11.
- Indexes beyond the FK and unique constraints. Add an index only if a
  query pattern in Block 03 demands it.
- Backfilling `agent_steps` / `agent_stopped_reason` for historical
  rows; those stay `NULL` for pre-F-11 runs.

## Schema Sketch

```sql
ALTER TABLE rag_query_runs
  ADD COLUMN execution_mode text NOT NULL DEFAULT 'single_shot'
    CHECK (execution_mode IN ('single_shot', 'agentic')),
  ADD COLUMN agent_steps int
    CHECK (agent_steps IS NULL OR agent_steps >= 0),
  ADD COLUMN agent_stopped_reason text
    CHECK (agent_stopped_reason IS NULL
           OR agent_stopped_reason IN ('finished', 'max_steps', 'error'));

CREATE TABLE rag_query_run_tool_calls (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  query_run_id    uuid NOT NULL REFERENCES rag_query_runs(id) ON DELETE CASCADE,
  step_index      int  NOT NULL CHECK (step_index >= 0),
  tool_name       text NOT NULL CHECK (tool_name IN ('search_corpus', 'search_document', 'list_documents')),
  args            jsonb NOT NULL,
  result_summary  jsonb NOT NULL,
  latency_ms      int  NOT NULL CHECK (latency_ms >= 0),
  created_at      timestamptz NOT NULL DEFAULT now(),
  UNIQUE (query_run_id, step_index)
);
```

## Acceptance Criteria

1. After running `pnpm db:migrate` on a fresh database, the new table
   exists with the schema above and `rag_query_runs` has the three new
   columns. Existing rows have `execution_mode = 'single_shot'` and
   `NULL` for the other two new columns.
2. Inserting two `rag_query_run_tool_calls` rows with the same
   `(query_run_id, step_index)` raises a unique-constraint error.
3. Deleting a `rag_query_runs` row cascades to its
   `rag_query_run_tool_calls` rows.
4. `ragQueryRunsRepository.persistAgenticRun` writes the parent row and
   all child rows in a single transaction; an error in either half
   rolls everything back.
5. Repository tests cover insertion, cascading delete, and the unique
   step-index constraint.

## Notes for Implementer

- Reuse the existing test harness that boots Postgres for repository
  tests (the project already does this for F-05/F-06 traces).
- Keep the migration purely additive. F-11 must not modify or drop any
  column from prior milestones.
- Do not pre-populate `execution_mode = 'agentic'` for any historical
  row.
